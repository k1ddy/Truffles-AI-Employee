- Five Whys:
  1. Why did booking stall: the system asked for `name` while `service` was still missing.
  2. Why was that accepted: collect plan validation only checked that the slot token is valid, not that slot order is valid.
  3. Why is that unsafe: booking flow lost contract continuity with `expected_reply_type=service_choice`.
  4. Why didn't deterministic boundary stop it: there is no collect-slot-order invariant in the boundary validator.
  5. Why is this architectural debt: single semantic owner still needs deterministic boundary validation for booking protocol invariants.

- Root cause statement:
  - booking collect plans are not validated against the required slot order invariant, so policy-core can legally jump to a later slot even when an earlier required slot remains missing.

- Fix mechanism:
  - compute earliest missing booking slot using the shared slot completeness contract
  - invalidate collect plans that target a later slot while an earlier one is still missing
  - degrade fail-closed into a traced booking prompt for the earliest missing slot
