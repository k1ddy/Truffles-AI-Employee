## Root cause (mandatory)

- Symptom:
  - `calendar.book_slot` currently treats only `service_query` and `start_at` as required at the policy verifier level
  - service execution can create an appointment even when `customer_name` and/or `customer_phone` are unresolved

- Minimal reproduction:
  1. inspect verifier contract:
     - `truffles-api/app/routers/webhook/decision.py`
     - `TOOL_VERIFIER_REQUIRED_FIELDS["calendar.book_slot"] = ("service_query", "start_at")`
  2. inspect tool execution:
     - `truffles-api/app/services/tool_registry_service.py`
     - `execute_tool_action(... tool_action="calendar.book_slot" ...)`
  3. inspect DB write path:
     - `truffles-api/app/services/appointment_service.py`
     - `SchedulingService.create_appointment(... commit=True)`

- Evidence:
  - `truffles-api/app/routers/webhook/decision.py`
    - verifier only hard-requires `service_query` and `start_at`
  - `truffles-api/app/services/tool_registry_service.py`
    - `resolved_customer_name = tool_args.get("customer_name") or user_name`
    - `resolved_customer_phone` can be `None`
    - `_book_slot(...)` is called immediately after that resolution
  - `truffles-api/app/services/appointment_service.py`
    - appointment is committed inside `create_appointment(... commit=True)`

- Five Whys:
  1. Why can a record be created without full contact: book-slot execution does not block on missing name/phone.
  2. Why does the boundary allow that: verifier contract models only slot availability inputs, not commit contract inputs.
  3. Why is that unsafe: a partial booking is already persisted before the business has a usable contact.
  4. Why does this violate the target architecture: booking commit protocol must be fail-closed on contract minimum, not best-effort.
  5. Why is this the first P3 slice: it is the cheapest high-impact guard before the later single-transaction bundling work.

- Root cause statement:
  - booking commit semantics are split: the runtime validates scheduling slots, but not the minimum contact contract required to persist an appointment.

- Fix mechanism:
  - centralize resolved contact-minimum computation (`name + phone`)
  - block `calendar.book_slot` before `_book_slot(...)` when contact minimum is incomplete
  - return explicit collect prompts (`name` or `phone`) and expose the reason in trace/meta
  - persist phone carryover in booking context so the next turn can complete the same booking flow without re-deriving semantics

## Invariant

1. No appointment row is created without resolved `name + phone`.
2. Missing contact minimum degrades into explicit collect, not silent fallback.
3. Contact collection remains business-agnostic and does not depend on demo-specific lexicons.
