  4. inspect `scripts/booking_dialog_scenarios.py` `_required_llm_tags()` / `_ensure_required_tags()` and `ops/diagnose.py` scenario-contract gate around `check_confirm_sequence_missing`

- Evidence:
  - Turn 5 is `check_booking`: runtime returns `calendar.get_booking -> not_found` and stays semantically coherent.
  - Turn 6 is forced `confirm`, but after a `not_found` lookup this is not a valid next act.
  - The generated scenario still requires `confirm` because generator currently injects `check_booking` and `confirm` together via `REQUIRED_BOOKING_CONFIRM_TAGS`, and the scenario-contract gate treats the combined sequence as mandatory.
  - The surfaced failure is expectation/state drift (`expected_state_mismatch`), not a tool/action regression on the booking-lookup turn.

- Five Whys:
  1. Why did `r24` fail: the confirm turn executed after a booking-lookup-not-found path and state no longer matched `bot_active`.
  2. Why was that confirm turn there: generator force-added `check_booking` and `confirm` to satisfy booking coverage.
  3. Why is that invalid: confirmation is not semantically guaranteed after a booking lookup; it belongs to a different family than `check_booking`.
  4. Why did oracle permit this contract: scenario-governance currently requires a hard `check_booking -> confirm` sequence instead of independent family coverage.
  5. Why did this surface now: `P1.6o24` removed the previous taxonomy drift, so the next invalid coverage assumption became the first failure.

- Root cause statement:
  - scenario-governance overconstrains booking coverage: it hard-requires `check_booking` and `confirm` as one sequence and generator enforces that per dialog, which produces semantically invalid turns even when runtime behavior is coherent.

- Fix mechanism:
  - change booking scenario-governance from forced `check_booking -> confirm` sequence to independent family coverage across the batch;
  - move missing-tag injection from per-dialog forced pair to batch-level helpers that can add `check_booking` and `confirm` separately.
