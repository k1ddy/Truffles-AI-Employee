- Symptom:
  - `P1.6o112` produced two consecutive invalid runs before scenario generation.
- Minimal reproduction:
  1. Inspect `/tmp/booking_quality/p1.6o112-l2-dev-20260312-a1-r1/summary.json` and `/tmp/booking_quality/p1.6o112-l2-dev-20260312-a1-r2/summary.json`.

  3. Inspect `ops/diagnose.py` and confirm `_llm_quality_openai_key_preflight(...)` caps timeout at `15s` even when `--judge-timeout=25.0`.
  4. Confirm `_run_openai_preflight_check(...)` fingerprints by `purpose|model|base_url|api_key`, so `llm` and `judge` repeat the same network probe when they share transport credentials.

  - `ops/diagnose.py`
- Five Whys:
  1. Why is `P1.6o112` blocked? Because hard OpenAI judge preflight times out before scenario execution.
  2. Why does judge preflight time out while llm preflight often passes? Because the second network probe repeats the same transport call and is still capped at `15s`.
  3. Why is that cap wrong? Because caller configuration already requests `--judge-timeout=25.0`, but the helper silently truncates it.
  4. Why do we repeat the probe? Because dedupe keys include `purpose`, so identical `llm`/`judge` transports are treated as different.
  5. Why is this an infra block, not product drift? Because no scenario executes and no new surfaced row is admitted; failure happens entirely in preflight.
- Root cause statement:
  - OpenAI preflight transport is over-strict and redundant: identical `llm`/`judge` transports probe twice, and the probe helper silently caps timeout at `15s`, causing repeat `invalid_openai_preflight` before any dialog evidence exists.
- Fix mechanism:
  - align OpenAI preflight timeout helper with configured timeout budget under a bounded cap;
  - reuse a successful preflight result across identical `api_key/model/base_url` transport tuples while keeping purpose-specific trace output;
  - add focused unit tests for timeout normalization and transport dedupe.
