## Root cause (mandatory)

- Symptom:
  - `r11` surfaced `На какое время лучше записаться?` under active booking and the runtime collapsed it into generic `booking_prompt`, which quality correctly reported as `booking_slot_stall`.
  - `P1.6o16b` already froze the taxonomy/oracle side, but runtime still has no owner path for the surfaced `ask_about_requested_slot(time)` act.

- Minimal reproduction:
  1. inspect `docs/TASK_PACKAGES/TP-2026-03-08-p1.6o16-booking-time-guidance-question-owner-a1.md`
  2. inspect `prompts/llm_policy_core.md` and `truffles-api/app/schemas/intent.py` for the missing output field that describes the interaction act relative to the active pending question
  3. inspect `truffles-api/app/routers/webhook/decision.py` around `_should_block_expected_reply_by_info`, policy-core payload extraction, and the `policy_tool_action == "collect"` booking branch
  4. inspect `truffles-api/tests/test_message_endpoint.py` around the expected-reply / question-like time tests

- Evidence:
  - policy-core currently models `subject_kind/capability/temporal_scope/resolution_mode`, but its output contract still has no field for `pending_question_act`
  - runtime therefore sees `collect + next_question=datetime`, but cannot distinguish `fill_requested_slot` from `ask_about_requested_slot`
  - the `collect` booking branch only knows how to emit a prompt for the missing slot; there is no bounded reply owner that answers the user's slot-question and then keeps the slot active
  - `P1.6o16b` already made the oracle fail-closed unless explicit pending-question interaction evidence exists, so runtime must now produce that evidence

- Five Whys:
  1. Why did `r11` stall: the response repeated slot collection without answering the user's slot-question.
  2. Why did runtime repeat slot collection: the collect branch only had generic prompt ownership for missing-slot turns.
  3. Why did the collect branch lack a distinct owner: policy-core output and runtime metadata had no explicit `pending_question_act` field to carry the interaction act.
  4. Why is that a runtime bug and not only an oracle bug: the system genuinely could not execute “answer the slot-question, then resume the same slot”.
  5. Why must this slice stay bounded: other families (`slot_compare`, `slot_constraint`, `mixed`) are still open and should not be silently absorbed into one overfitted fix.

- Root cause statement:
  - the runtime collect path is missing a policy-owned interaction-act signal and a bounded owner for `ask_about_requested_slot(time)`, so a live slot-question still degenerates into generic slot prompting.

- Fix mechanism:
  - extend the policy-core prompt/schema/output validation with `pending_question_act`
  - extract and propagate that field into `decision_meta` / `decision_trace`
  - add one bounded runtime owner in the booking collect branch for `ask_about_requested_slot(time)` that emits guidance plus resume-contract evidence while keeping `expected_reply_type=time`
  - prove it with focused deterministic tests
