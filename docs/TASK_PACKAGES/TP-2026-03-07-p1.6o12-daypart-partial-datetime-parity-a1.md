- Ready solutions found:
  - datetime resolution keeps separate temporal components such as `dayPart`, so daypart-only input is meaningful temporal evidence but not the same thing as a fully specified appointment datetime;
  - slot contracts should preserve that partial evidence instead of dropping it or treating it as a fully complete timestamp.
- Decision (`reuse/integrate/build`): `reuse + integrate`
  - reuse the existing booking signal helpers for daypart extraction and the existing partial-datetime discipline from `P1.6h`;
  - integrate them into expected-reply matching and booking completeness so daypart-only values are preserved as partial time context but do not prematurely complete booking.
- Rejected options:
  - weakening `booking_slot_stall` oracle for daypart-only turns;
  - keeping daypart-only values invisible to expected-reply matching;
  - treating bare daypart as fully complete `datetime` and advancing booking to `name`.

- Evidence:
  - failing turn meta is `action=booking_prompt`, `intent=booking`, `expected_reply_type=time`, `expected_reply_blocked_by_info=true`, `expected_reply_matched=false`
  - policy-core payload correctly keeps booking on `next_question=datetime`
  - trace shows `question_contract decision=missed answer_error=blocked_by_info`
  - current booking completeness helper `_is_datetime_grounded_for_prompt()` treats bare daypart values as grounded/completed datetime
  - current expected-reply validator `_validate_datetime_slot()` does not preserve daypart-only values like `на утро`

- Five Whys:
  1. Why did guarded quality fail: the system repeated a generic datetime prompt without recording any time-slot progress.
  2. Why was there no progress: expected-reply matching did not capture the daypart answer.
  3. Why did expected-reply matching miss it: `_validate_datetime_slot()` only accepts extracted datetime or hour fallback, not daypart-only temporal values.
  4. Why is that still a contract mismatch: booking prompt completeness currently treats daypart-only values as if they were already grounded datetime, so validator/completeness disagree on the same temporal token.
  5. Why is this not just oracle noise: the runtime loses user-provided temporal evidence (`утро`) and falls back to a fully generic prompt, which is a real booking continuity defect.

- Root cause statement:
  - daypart-only temporal values are modeled inconsistently across expected-reply validation, info-block arbitration, and booking datetime completeness: the runtime neither preserves them as partial booking progress nor treats them under one deterministic completeness rule.

- Fix mechanism:
  - let expected-reply validation capture daypart-only temporal values as partial datetime progress
  - narrow the `EXPECTED_REPLY_TIME` info-block rule so captured daypart answers are not discarded
  - tighten booking datetime completeness so daypart-only values remain incomplete unless paired with a date or exact clock time
  - prove the new single rule with exact low-level and message-endpoint tests

## Invariant

1. Daypart-only values (`утром`, `после обеда`, `вечером`) are preserved as partial time context, not discarded.
2. Daypart-only values do not fully complete booking by themselves; booking may still require follow-up on date/time.
3. Existing explicit clock-time and date+daypart flows must not regress.
4. No oracle weakening or phrase-hardcode branch in core.
