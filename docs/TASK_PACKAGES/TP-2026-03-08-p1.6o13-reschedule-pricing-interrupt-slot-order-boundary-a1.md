- Five Whys:
  1. Why did guarded quality fail: the runtime replied with a generic booking prompt instead of an info-owned pricing clarify/reply.
  2. Why did it send a booking prompt: collect validation raised `collect_slot_order_invalid` and immediately degraded to `service_choice`.
  3. Why did collect validation raise: the plan requested `datetime` while the earliest booking slot was still `service`.
  4. Why is that the wrong owner: the same turn also has explicit pricing interrupt semantics and `expected_reply_blocked_by_info=true`, so it should first pass through the info-interrupt owner path.
  5. Why does this still happen: the validator runs before the existing info-interrupt arbitration, so the runtime never reaches the correct owner.

- Root cause statement:
  - booking collect slot-order validation is applied too early to policy-core `collect` plans that are actually info interruptions, so the runtime exits on `collect_slot_order_invalid` before `policy_collect_info_interrupt_owner` can convert the turn into the correct info-owned path.

- Fix mechanism:
  - detect info-interrupt ownership candidate before enforcing booking slot-order validation;
  - exempt those turns from early `collect_slot_order_invalid`;
  - let the existing late `policy_collect_info_interrupt_owner` path own the turn and route it into pricing/service clarify or info reply contract;
  - prove the behavior with exact message-endpoint and quality-guard regressions.
