  - `r15` is the first `infra_valid=true` run in this chain, so the surfaced family is admissible semantic evidence even though the run is partial (`dialogs_seen=1/10`).
  - On the failing turn, `decision_meta` shows `policy_core_mode=degraded_fallback`, `policy_core_degrade_reason=policy_error:timeout`, `action=reply`, `intent=policy_core_guard`, and `clarify_reason=timeout_degrade`.
  - The response body is generic clarify (`Подскажите, пожалуйста, что именно вас интересует?`), `expected_reply_type` is missing, and trace contains only `llm_policy_core` timeout + `llm_policy_plan_delta reason=policy_core_timeout_degrade_clarify`.
  - The scenario expectation is contract-based: `pending_question_act=ask_about_requested_slot`, `pending_question_target=time`, `expected_reply_type=time`, plus trace stages `pending_question_interaction` and `question_contract`.
  - The same family is already modeled in the normal LLM-owned path by `P1.6o16`, but timeout degraded collect currently falls through to generic booking/clarify prompts and never replays the pending-question contract.

- Five Whys:
  1. Why did `r15` fail: timeout degraded policy-core replied with generic clarify instead of preserving the active time-slot question contract.
  2. Why did it use generic clarify: the timeout degraded collect boundary only distinguishes booking collect vs generic clarify, not `fill_requested_slot` vs `ask_about_requested_slot(time)`.
  3. Why does that distinction disappear under timeout: the normal owner (`P1.6o16`) is only wired for successful policy-core semantic output, while timeout fallback uses a reduced deterministic path.
  4. Why is that wrong: active booking collect still has a requested slot (`datetime`) and the user turn is about that slot, so the runtime must preserve resume/evidence even when semantic-owner timed out.
  5. Why did this surface only after `P1.6o19`: previous adjacent families were closed, so the next blocker moved deeper into the timeout/degrade boundary for the same pending-question axis.

- Root cause statement:
  - timeout degraded booking-collect fallback compresses active requested-slot questions into the generic clarify/booking prompt path, so the runtime loses `pending_question_interaction` semantics and drops the `expected_reply_type=time` resume contract exactly when policy-core times out.

- Fix mechanism:
  - add one bounded timeout-only fallback for active `expected_reply_type=time` slot-question turns that preserves `pending_question_interaction`, keeps `question_contract.expected_reply_type=time`, and responds with a safe booking-side reply instead of generic clarify;
  - keep the fix contract-first and bounded by active booking collect + timeout degrade + requested-slot question signals, with deterministic regressions proving no fallback to generic clarify for this family.
