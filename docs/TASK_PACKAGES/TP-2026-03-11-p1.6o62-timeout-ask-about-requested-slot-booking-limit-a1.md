- Five Whys:
  1. Why did `r81` fail: the bot escalated to pending instead of preserving the active requested-slot question contract.
  2. Why did it escalate: the second `policy_core` timeout in the same booking collect chain triggered `timeout_booking_limit` and `policy_timeout_degrade`.
  3. Why did the limit trigger on turn `2`: the first degraded collect on turn `1` had already incremented the shared `policy_timeout_degrade` clarify counter.
  4. Why is that wrong for this row: the user is still operating over the same unresolved `time` slot, so repeated timeout degrade must preserve `ask_about_requested_slot(time)` semantics before any generic handoff is allowed.
  5. Why is this a new bounded family rather than a reopen of `P1.6o59`/`P1.6o61`: active semantic ownership for free-slot questions and grounded specialist availability is already closed on bounded contour; the remaining gap is row-blind clarify-limit escalation under repeated timeout pressure.

- Root cause statement:
  - `policy_timeout_degrade` currently shares one conversation-level clarify budget across degraded booking collect and later active slot-question turns; once the first degraded collect consumes the single retry, the next timeout on an open `ask_about_requested_slot(time)` row escalates to pending before the row-specific degrade owner can preserve `question_contract` and `pending_question_interaction`.

- Fix mechanism:
  - publish a new matrix row (`M11`) for repeated-timeout active slot-question handling under active `time` collect;
  - preserve `ask_about_requested_slot(time)` degrade ownership, `question_contract.expected_reply_type=time`, and trace/meta evidence even when the prior turn already used degraded collect;
  - move escalation behind a row-scoped timeout limit instead of inheriting the generic booking-collect clarify count;
  - add deterministic regressions for the exact sequence `degraded_collect -> ask_about_requested_slot(time) -> timeout`.
