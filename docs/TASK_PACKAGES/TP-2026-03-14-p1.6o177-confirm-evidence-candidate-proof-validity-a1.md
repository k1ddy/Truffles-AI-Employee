## Root cause (mandatory)

- Symptom:
  - `P1.6o176` completed and strict-audited with `artifact_integrity.valid=true`, but remained `infra_valid=false` because `tool_evidence.reasons=['confirm_candidate_missing']`.
- Minimal reproduction:
  1. run guarded `dev L2` proof lane on `:18184` with strict `tool_evidence`;
  2. let the executed prefix observe a confirm path (`confirm_tool_events=1`, `confirm_hook_events=1`, `booking_confirm_trace_events=1`) without a separate `check_booking` turn or `booking_confirm` action counter;
  3. inspect `summary.json` and `manual_audit.json`;
  4. observe that strict `tool_evidence` still marks the run infra-invalid only because `confirm_candidates == 0`.
- Evidence:
  - `/tmp/booking_quality/p1.6o176-l2-dev-20260314-a1-r1/summary.json`
  - `/tmp/booking_quality/p1.6o176-l2-dev-20260314-a1-r1/brief.md`
  - `/tmp/booking_quality/p1.6o176-l2-dev-20260314-a1-r1/responses.jsonl`
  - `/tmp/booking_quality/p1.6o176-l2-dev-20260314-a1-r1/trace_bundle.jsonl`
  - `/tmp/booking_quality/p1.6o176-l2-dev-20260314-a1-r1/manual_audit.json`
- Five Whys:
  1. Why is the rerun infra-invalid? Because strict `tool_evidence` appends `confirm_candidate_missing`.
  2. Why does it append that reason? Because `_llm_quality_build_tool_evidence_status(...)` derives `confirm_candidates` only from `check_booking_intents + booking_confirm_actions`.
  3. Why is that wrong on the surfaced run? Because the same run already has observed confirm evidence: `confirm_tool_events=1`, `confirm_hook_events=1`, and `booking_confirm_trace_events=1`.
  4. Why does that become self-contradictory? Because the gate both requires confirm proof and ignores the very trace/tool evidence that proves the confirm path happened.
  5. Why is this a proof-validity bug, not a new runtime family? Because the surfaced blocker lives entirely in `ops/diagnose.py`; runtime behavior already emitted confirm evidence.
- Root cause statement:
  - strict `tool_evidence` treats confirm opportunity as candidate-free unless it sees `check_booking` intents or `booking_confirm` actions, so runs with observed confirm trace/tool/hook evidence but no separate candidate label are falsely marked `confirm_candidate_missing`.
- Fix mechanism:
  - make `confirm_candidate_missing` impossible when observed confirm evidence already exists, while keeping strict confirm evidence/hook requirements intact once a real confirm opportunity is present.
