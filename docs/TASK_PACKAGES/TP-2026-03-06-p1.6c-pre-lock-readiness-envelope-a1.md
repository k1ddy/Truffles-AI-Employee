- Five Whys:
  1. Why are guarded acceptance runs not effective now: they are started before readiness inputs exist.
  2. Why is that expensive: each failed attempt creates non-canonical artifacts and more audit debt.
  3. Why does that slow closure: process-trust gates start blocking future runs instead of helping promotion.
  4. Why is the team tempted to brute-force the chain: the workflow did not explicitly separate readiness evidence from promotion runs.
  5. Why is the right fix a readiness envelope: acceptance chain should remain strict, but only after cheaper evidence proves the branch is ready.

- Root cause statement:
  - The current workflow still implicitly treats guarded acceptance runs as a debugging loop, while the chain controller is designed for promotion-only use after readiness inputs (`manual_audit`, `L1/L2 evidence`, `PG checklist`, runtime contract) are already green.

- Fix mechanism:
  - Make readiness-first explicit in TP/runbook.
  - Build `L1` and `dev L2` evidence first, close all pending audits, assemble `PG checklist`, and only then start guarded acceptance `lock`.
