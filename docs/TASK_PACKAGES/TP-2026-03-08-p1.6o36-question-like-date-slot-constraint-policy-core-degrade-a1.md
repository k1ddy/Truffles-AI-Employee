- Evidence:
  - scenario expects:
    - `pending_question_act=slot_constraint`
    - `pending_question_target=time`
    - `question_contract expected_reply_type=time`
  - runtime actually does:
    - `question_contract decision=missed` with `answer_error=blocked_by_info`

    - `policy_core_mode=degraded_fallback`

  - judge verdict is `fail` because the bot asks for unnecessary clarification instead of answering the booking/time question.
  - therefore `r37` surfaces a real runtime boundary defect, not taxonomy drift.

- Five Whys:
  1. Why did `r37` fail: runtime replied with `info_clarify` instead of booking/time guidance or slot-progress.
  2. Why did runtime choose `info_clarify`: question-contract blocked the turn as `blocked_by_info` before preserving the time-slot constraint semantics.
  3. Why did policy-core not recover it: the downstream policy-core output hit `invalid_schema`, so runtime degraded instead of keeping booking collect.
  4. Why is this wrong architecturally: question-shaped date constraints under active `expected_reply_type=time` are part of the booking collect contract, not an info-clarify family.
  5. Why did it surface now: `P1.6o34` and `P1.6o35` removed adjacent taxonomy overclaims, exposing the real runtime loss on question-like date constraints.

- Root cause statement:
  - the runtime boundary still lets info-like/question-like heuristics block active `time` slot-constraint turns before the booking question-contract can preserve their collect semantics, and once policy-core then fails schema validation, the turn degrades to generic `info_clarify` instead of bounded booking resume.

- Fix mechanism:
  - adjust the booking/time question-contract and/or policy-core degrade boundary so question-shaped date slot-constraints under active `expected_reply_type=time` keep bounded booking collect semantics;
  - add deterministic regressions at endpoint/guard level;
  - then run one fresh guarded rerun `r38`.
