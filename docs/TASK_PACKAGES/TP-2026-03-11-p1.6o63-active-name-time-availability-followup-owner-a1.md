- Five Whys:
  1. Why did `r82` fail: the bot ignored the user's availability question about `15:00` and repeated a generic name prompt.
  2. Why did runtime repeat the name prompt: once the dialog had already advanced to `expected_reply_type=name`, the collect branch had no bounded owner for a side-question about time availability and fell through to generic `booking_prompt`.
  3. Why was there no bounded owner: current preservation logic only models `ask_about_requested_slot(time)` while active collect is still `time`, plus specialist follow-up rows during `time/name` collect.
  4. Why did policy-core not protect the row first: it mis-targeted the turn as `pending_question_target=specialist` / `subject_kind=booking` even though the user was probing alternate specific-time availability.
  5. Why did the run also show expectation drift: scenario governance has no canonical normalization for alternate-time availability probes under active `name` collect, so the generated turn drifted to stale `service_choice`; this makes the run non-canonical, but the judge-failing product behavior remains real.

- Root cause statement:
  - after grounded time fill advances booking to active `name` collect, the system has no explicit row for alternate specific-time availability follow-ups over the already-filled `datetime` axis; policy-core mislabels the interaction target, runtime only preserves requested-slot ownership for active `time` collect and therefore drops `pending_question_interaction` under `name` collect, and scenario governance still falls back to stale `service_choice` expectations for the same family.

- Fix mechanism:
  - publish a new matrix row (`M12`) for active-`name` alternate-time availability follow-up;
  - make policy-core/runtime preserve `pending_question_target=time`, `active_question_relation=ask_about_requested_slot`, and `expected_reply_type=name` on this row;
  - answer truthfully about the alternate slot without silently overwriting committed `booking.datetime`;
  - normalize scenario expectations so this family no longer drifts to `service_choice`;
  - add deterministic regressions for prompt/runtime/scenario boundaries before the next guarded rerun.
