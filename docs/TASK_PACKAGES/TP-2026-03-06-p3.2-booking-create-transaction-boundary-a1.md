## One web search (mandatory before implementation)

- Query: `SQLAlchemy session begin nested transaction flush commit savepoint docs`
- Time (UTC): `2026-03-06T12:15:00+00:00`

- Ready solutions found:
  - logical unit-of-work should avoid commit-as-you-go when later steps are part of the same business outcome
  - `flush` can materialize rows inside the transaction boundary without final commit
  - nested/savepoint transaction boundaries are appropriate when a local write cluster must roll back without leaving partial side effects
- Decision (`reuse/integrate/build`): `reuse + integrate`
  - reuse existing `commit=False` support already present in appointment/calendar/reminder services
  - integrate a booking-create transaction boundary around the existing service calls instead of introducing a parallel write path
- Rejected options:
  - keep internal commits and try to compensate with best-effort cleanup
  - add another post-hoc reconciler to delete partial rows after failure
  - move booking create into a demo-specific fast path

## Root cause (mandatory)

- Symptom:
  - `calendar.book_slot` create-path can persist appointment, then separately persist outbox and reminders, while user/profile/context sync continues later in request flow.
  - A failure after `create_appointment(... commit=True)` leaves a committed appointment without the rest of the contract.

- Minimal reproduction:
  1. inspect create-path in `truffles-api/app/services/tool_registry_service.py`
  2. inspect `SchedulingService.create_appointment(... commit=True)` in `truffles-api/app/services/appointment_service.py`
  3. inspect `enqueue_appointment_sync(... commit=True)` in `truffles-api/app/services/calendar_sync_service.py`
  4. inspect `schedule_default_reminders(... commit=True)` in `truffles-api/app/services/appointment_reminder_service.py`
  5. inspect post-tool profile sync in `truffles-api/app/routers/webhook/decision.py`

- Evidence:
  - `truffles-api/app/services/tool_registry_service.py`
    - create-path currently calls `_book_slot(...)`, `enqueue_appointment_sync(... commit=True)`, `schedule_default_reminders(... commit=True)`
  - `truffles-api/app/services/appointment_service.py`
    - `create_appointment(... commit=True)` performs immediate DB commit
  - `truffles-api/app/routers/webhook/decision.py`
    - `sync_user_profile_from_booking_args(...)` happens after tool execution, so internal commits can precede profile sync

- Five Whys:
  1. Why can partial booking state persist: create-path commits each stage independently.
  2. Why does that happen: service helpers default to `commit=True` and tool orchestration uses them directly.
  3. Why is that unsafe: later failure cannot roll back already committed appointment/outbox/reminder writes.
  4. Why does this violate the target architecture: booking commit must be fail-closed and atomic for the whole business outcome, not per helper.
  5. Why is this the next slice after `P3.1`: contact minimum now blocks obviously invalid create attempts, so the next dominant defect is partial commit after valid contact.

- Root cause statement:
  - booking create-path is implemented as commit-as-you-go across multiple helpers instead of a single transactional unit-of-work scoped to the request.

- Fix mechanism:
  - introduce a dedicated booking-create write boundary in the tool path
  - switch appointment create, calendar outbox enqueue, reminder scheduling to `commit=False` inside that boundary
  - flush for ids/rows, but do not commit inside helper calls
  - ensure rollback clears appointment/outbox/reminder writes when downstream step fails before request-level commit
  - keep profile sync inside the same outer request transaction so it is no longer downstream of already committed appointment data

## Invariant

1. `calendar.book_slot` create-path must not leave committed partial booking side effects.
2. Deterministic layer may enforce transaction boundaries, but must not change semantic owner decisions.
3. The implementation must stay pack-agnostic and branch-aware.
