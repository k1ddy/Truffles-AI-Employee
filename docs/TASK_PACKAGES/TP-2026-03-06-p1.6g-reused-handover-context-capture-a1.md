- Five Whys:
  1. Why did stale booking expectation survive: active handover was reused instead of created fresh.
  2. Why is reuse different: `_reuse_active_handover(...)` skipped pending snapshot/clear logic.
  3. Why does that matter: bot kept live booking expected-reply/session state while conversation was effectively manager-owned.
  4. Why did later turn stall: next inbound turn was still evaluated against stale booking expectation even though the handover path had already taken over.
  5. Why is this architectural debt: two pending-entry paths had different state-transition contracts.

- Root cause statement:
  - reused-handover transition was not using the same pending snapshot/clear contract as `escalate_to_pending`, so manager-owned reuse left live booking expected-reply state in runtime and polluted later turns.

- Fix mechanism:
  - apply the existing pending snapshot/clear contract on handover reuse before/while transitioning into `pending/manager_active`
  - keep the fix at the transition boundary, not in downstream semantic handlers
  - add deterministic contract tests for reused handover from `bot_active` and from already `pending`

## Invariant

1. Handover reuse must preserve resume capability without leaving live booking expected-reply state active.
2. No semantic hardcode is added to fix the stall.
3. Pending/handoff ownership stays deterministic-boundary only: snapshot, clear, resume.
