- Symptom:
  - `P1.6o170` strict-audited rerun is `infra_valid=true`, `semantic_valid=false` and surfaces `dialog 2 / turn 4 / "Какой у вас график работы?"`, where scenario still requires `reply_type=time`, `meta_any.expected_reply_type=["time"]`, and `question_contract.expected_reply_type=time`, but runtime canonically answers pure `hours` info with no active booking follow-up evidence.
- Minimal reproduction:
  1. Inspect `/tmp/booking_quality/p1.6o170-l2-dev-20260314-a1-r1/scenarios.json` dialog `2` turns `3-4` and confirm turn `3` (`"Мне нужен маникюр и педикюр."`) already advances to `reply_type=time`, which makes turn `4` inherit stale `time` continuity on `hours`.

  3. Inspect `scripts/booking_dialog_scenarios.py` and confirm `_looks_like_service_grounded_booking(...)` treats any service token hit as grounded, so a multi-service request like `"маникюр и педикюр"` over-advances to `time`.
  4. Confirm sanitize/repair then leave that stale follow-up state in place, so the later `hours` interrupt inherits a bogus `question_contract.expected_reply_type=time`.

- Five Whys:
  1. Why did the `hours` turn fail? Because scenario still required active `time` continuity.
  2. Why did scenario require `time` continuity? Because the preceding multi-service booking request was incorrectly treated as a grounded single-service booking.
  3. Why was it treated as grounded? Because service grounding currently accepts any one service token hit and does not detect unresolved multi-service requests.
  4. Why did the stale state leak into the `hours` turn? Because sanitize/repair preserved the over-advanced continuation instead of clearing it at the clarification boundary.
  5. Why is this architectural debt? Because scenario compiler carries stale semantic context past a clarify state and invents a second booking path that runtime does not actually follow.
- Root cause statement:
  - scenario compiler over-grounds multi-service booking requests and leaks stale `time` follow-up context into later info interrupts, producing a second semantic path that runtime never takes.
- Fix mechanism:
  - add a bounded multi-service clarify detection path that compiles unresolved multi-service booking back to `service_choice` and explicitly clears stale follow-up continuity for subsequent info interrupts in the same contour;
  - add targeted sanitize/repair regressions for the surfaced multi-service -> hours sequence.
