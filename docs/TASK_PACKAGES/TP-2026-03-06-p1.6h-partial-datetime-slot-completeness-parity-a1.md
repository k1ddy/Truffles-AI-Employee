## Root cause (mandatory)

- Symptom:
  - guarded `dev L2` run `p1.6-l2-dev-seed42-r14` produced `booking_slot_stall` on dialog `8` turn `13`
  - after `calendar.list_slots` returned no exact slot and set `expected_reply_type=time`, the next user message `Меня зовут Динара.` still led policy-core to ask for `name` instead of keeping the booking on `time`

- Evidence:
  - `/tmp/booking_quality/p1.6-l2-dev-seed42-r14/trace_bundle.jsonl`
    - turn `12`: `question_contract` sets `expected_reply_type=time`
    - turn `12`: `llm_policy_core.memory_active_slots=["service","datetime"]`
    - turn `13`: `llm_policy_core.next_question=name` while `memory_expected_reply_type=time`
  - `truffles-api/app/routers/webhook/booking.py`
    - `_next_booking_prompt(...)` already treats date-only datetime as incomplete and keeps `last_question=datetime`
  - `truffles-api/app/routers/webhook/decision.py`
    - policy-core memory profile currently marks any non-empty `booking.datetime` as active
    - tool-followup / completeness checks also use non-empty string truthiness for `datetime`

- Five Whys:
  1. Why did policy-core ask for `name`: input state still advertised `datetime` as active.
  2. Why was `datetime` advertised as active: policy-core memory/profile and contract checks only tested non-empty string, not slot completeness.
  3. Why is that inconsistent: booking prompt contract already knows that date-only datetime is incomplete.
  4. Why did stall appear only in realism: list-slots/no-availability path preserved coarse date context (`завтра`) and exposed the mismatch between semantic memory and booking prompt state.
  5. Why is this architectural debt: the same booking slot had two different completeness rules in adjacent owners.

- Root cause statement:
  - booking datetime completeness is not represented consistently across booking prompt, policy-core memory input, and deterministic tool contracts; date-only values leak as if `datetime` were complete, so policy-core can legitimately progress to `name` even while boundary state still requires `time`.

- Fix mechanism:
  - reuse the existing booking completeness rule for `datetime` (grounded time/daypart required)
  - apply it consistently to policy-core memory/profile and deterministic booking completeness checks
  - make contract tests prove that date-only datetime does not count as active/complete in these paths

## Invariant

1. Booking slot completeness is single-rule across semantic and deterministic layers.
2. Date-only `datetime` remains useful context, but not a complete slot.
3. No keyword/lexicon hardcode is added in core.
4. No post-hoc semantic rewrite from `name` to `time` is introduced as the primary fix.
