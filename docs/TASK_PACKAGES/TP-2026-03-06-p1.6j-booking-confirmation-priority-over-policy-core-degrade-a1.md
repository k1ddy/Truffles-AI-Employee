- Five Whys:
  1. Why did the conversation stay in `pending`: policy-core ran on a booking confirmation turn and degraded into pending hold.
  2. Why was policy-core allowed to run: runtime eligibility did not short-circuit on `booking.confirmation`.
  3. Why is that wrong: the active confirmation slot is still owned by the booking protocol, not by policy-core arbitration.
  4. Why didn't deterministic boundary prevent it: the boundary had no explicit priority rule for booking confirmation over policy-core runtime.
  5. Why is this architectural debt: single-owner semantics still leaked because two owners could act on the same unresolved slot turn.

- Root cause statement:
  - unresolved booking confirmation was not modeled as a higher-priority bot-owned protocol state, so policy-core/degraded runtime could consume that turn and re-enter pending/handoff logic.

- Fix mechanism:
  - treat `booking.confirmation` as a hard priority guard before policy-core runtime activation
  - record observable trace/meta when policy-core is skipped for this reason
  - add regression coverage proving confirmation turns stay bot-active and do not call policy-core

## Invariant

1. Pending booking confirmation stays owned by the booking protocol until resolved.
2. Deterministic boundary may block policy-core runtime on confirmation turns, but must not reinterpret the turn semantically.
3. The skip must be observable in trace/meta with an explicit reason.
