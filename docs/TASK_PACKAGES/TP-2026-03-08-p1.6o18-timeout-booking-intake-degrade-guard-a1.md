  - Deterministic probe confirms that for the same surface form `_is_booking_request(...) == True`, `_looks_like_info_query(...) == True`, and `get_pack_service_hint(...) == Маникюр`.
  - Timeout-degrade guard currently suppresses booking-request protection whenever `_looks_like_info_query(...)` is true, so the bounded booking-collect path is skipped and `pack_fact_fallback` becomes eligible.

- Five Whys:
  1. Why did `r13` fail on the first turn: timeout degrade produced a fact-like fallback reply without evidence.
  2. Why did timeout degrade choose fact fallback: the bounded booking-collect timeout path did not activate.
  3. Why did the booking-collect timeout path not activate: `timeout_booking_request_signal` was forced false when the same text also matched `_looks_like_info_query(...)`.
  4. Why is that wrong: `Здравствуйте, хочу записаться на маникюр.` is still a booking-intake collect turn, even if broad info heuristics also fire on the surface.
  5. Why did this only surface in `r13`: previous blocks closed pending-question families, so the next blocker came from timeout/degrade interaction on an earlier booking-intake boundary.

- Root cause statement:
  - the timeout degraded booking guard over-trusts `_looks_like_info_query(...)` and lets that generic heuristic suppress booking-request protection, so first-turn booking intake with a service hint can collapse into `pack_fact_fallback` under policy timeout/deadline.

- Fix mechanism:
  - preserve timeout booking-request protection whenever `_is_booking_request(...)` is true, then let the existing bounded booking-collect timeout path handle service-hint collect;
  - add deterministic regression proving booking collect still wins even when `booking_request=true` and `looks_like_info_query=true` on the same turn.
