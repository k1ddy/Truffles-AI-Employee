- Evidence:
  - `llm_policy_core` payload for the failing turn carries:
    - `goal=booking`
    - `action=collect`
    - `next_question=datetime`
    - `pending_question_target=specialist`
  - the same payload does not carry specialist in `tool_args` or `entity_refs`
  - runtime therefore falls through to generic `booking_prompt` for `datetime` and loses explicit specialist-followup evidence
  - existing `P1.6o37` deterministic test covered the variant where semantic payload already contained `entity_refs=[master:Айгерим]`, so it did not cover the missing-referent branch surfaced by `r40`

- Five Whys:
  1. Why did `r40` fail: scenario expected specialist-followup trace/meta, but runtime emitted plain `booking_prompt`.
  2. Why did runtime emit plain `booking_prompt`: `specialist_followup` is only armed when runtime can extract specialist preference from `tool_args` or `entity_refs`.
  3. Why was no preference extracted: policy-core marked `pending_question_target=specialist` but omitted explicit specialist referent in the payload.
  4. Why did previous coverage miss it: deterministic regression only covered the grounded semantic-referent variant.
  5. Why is this an architecture gap rather than phrase drift: the missing capability is owner recovery from an existing semantic contract, not recognition of one literal phrase.

- Root cause statement:
  - booking specialist follow-up ownership in collect-state currently depends on fully grounded specialist referents inside the policy-core payload; when policy-core preserves the target axis (`pending_question_target=specialist`) but omits the explicit referent, runtime has no bounded recovery path and collapses the turn into generic time collect.

- Fix mechanism:
  - keep specialist ownership gated by the existing semantic contract (`goal=booking`, active collect, `pending_question_target=specialist`);
  - when explicit specialist referent is missing, reuse the existing secondary `extract_specialist_hint_llm` helper to recover only the missing specialist preference;
  - persist recovered specialist preference into booking state and emit canonical `pending_question_interaction=booking_specialist_followup` evidence;
  - cover it with deterministic runtime regression, then rerun guarded `dev L2`.
