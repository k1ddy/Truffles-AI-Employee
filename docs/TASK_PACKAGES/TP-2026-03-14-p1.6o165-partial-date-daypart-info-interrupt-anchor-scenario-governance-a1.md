- Five Whys:
  1. Why did proof fail? Because the scenario expected `name` while runtime trace/meta kept `time`.
  2. Why did the scenario expect `name`? Because grounded partial-date daypart normalization fired on the slot-question turn.
  3. Why did that normalization fire? Because `partial_date_anchor_active` was still `True`.

- Root cause statement:
  - scenario-governance keeps `partial_date_anchor_active` across generic non-progress info interrupts, so a later grounded daypart slot question and downstream pricing turn inherit stale `name` expectations that contradict the actual runtime contract.
- Fix mechanism:
  - reset the partial-date anchor when the current turn is a generic active info interrupt unless the expectation explicitly encodes booking-progress continuity via `expected_reply_contract_reason=catalog_service_booking_progress`;
  - add a regression proving that `partial-date -> hours -> grounded daypart slot question -> pricing` stays on `reply_type=time` while still preserving the existing service-grounded booking-progress path.
