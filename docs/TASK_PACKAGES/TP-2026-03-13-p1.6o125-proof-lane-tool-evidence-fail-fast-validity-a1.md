- Symptom:
  - `P1.6o124` stopped at `max_failures_reached:1` on `dialog 1 / turn 9`, but the run became non-canonical because `infra_valid=false` via `tool_evidence:{calendar_intent_missing,calendar_evidence_missing,confirm_candidate_missing,confirm_evidence_missing,calendar_hook_missing,confirm_hook_missing}`.

  3. Confirm `_llm_quality_build_tool_evidence_status()` still required calendar/confirm evidence because booking coverage was present, even though no observed calendar/check-booking/confirm opportunity existed before the stop point.
  4. Confirm this forced `infra_valid=false`, which blocks truthful class routing under `P1.6o118`.

- Five Whys:
  1. Why is `P1.6o124` non-canonical? Because `infra_valid=false`.
  2. Why is `infra_valid=false`? Because strict tool-evidence declared calendar/confirm evidence missing.
  3. Why did tool-evidence declare them missing? Because booking coverage token alone made calendar/confirm evidence required.
  4. Why is that wrong on this run? Because fail-fast stopped the run before any observed calendar/check-booking/confirm opportunity existed in the executed prefix.
  5. Why does that matter architecturally? Because proof-lane routing then gets blocked by a tooling validity false-positive instead of a true runtime/preflight failure.
- Root cause statement:
  - strict tool-evidence currently keys off broad booking coverage rather than observed tool opportunity/evidence, so fail-fast proof runs can become infra-invalid from unexecuted downstream booking tails.
- Fix mechanism:
  - make strict tool-evidence require calendar/confirm only when the executed turn set has already observed the corresponding calendar/check-booking/confirm opportunity or evidence;
  - keep full acceptance semantics intact by preserving strict evidence requirements once such opportunity/evidence is present;
  - add regression tests for fail-fast proof prefixes and existing strict positive/negative cases.
