    - policy-core returned `collect` or `info/catalog.service_query` inconsistently for the same service-present master-availability question
  - `truffles-api/app/services/pack_runtime_service.py`
    - resolver required `person + action/experience` or `direct_signal`, so `специалист + service + question` was still non-explicit

- Five Whys:
  1. Why did the user get pricing: policy-core classified the question as generic info and tool path executed `catalog.service_query`.
  2. Why didn’t master guard catch it: resolver did not treat `person + concrete service + question` as explicit master intent.
  3. Why did policy-core drift to `collect`: prompt contract did not clearly distinguish `service-present master availability` from `service-missing master collect`.
  4. Why is that unstable: abstract rules existed, but the failing edge case had no explicit representative example.
  5. Why does this matter architecturally: single-owner remains weak if the owner prompt and boundary resolver disagree on a common open-world phrasing.

- Root cause statement:
  - master-availability questions with a concrete service were underspecified in both policy-core prompt and resolver contract, so the owner and boundary layer disagreed on whether the service was explicit and whether the turn belonged to `master_query`.

- Fix mechanism:
  - tighten resolver contract so `person + service + question-like` becomes explicit `master_query` unless conflicting info-scope signals exist
  - strengthen policy-core prompt with explicit rule and counterexample pair:
    - service-present specialist availability -> `master_query fact`
    - service-missing specialist request -> `master_query collect`
  - keep message-endpoint guard contract covered so misplanned `catalog.service_query` cannot leak pricing once the master signal is explicit

## Invariant

1. No new phrase/regex routing is added to runtime core.
2. `master_query` stays LLM-owned; deterministic logic only enforces the boundary contract when the master signal is explicit.
3. Service-present specialist availability questions must not degrade to `collect` or leak `pricing`.
