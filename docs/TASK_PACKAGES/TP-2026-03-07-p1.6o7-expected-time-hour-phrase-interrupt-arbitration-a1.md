- Five Whys:
  1. Why did slot progress stall: the expected-reply contract never accepted the turn as a valid `time` answer.
  2. Why was the answer rejected: `_should_block_expected_reply_by_info()` marked the message as info/duration interruption before slot matching could be applied.
  3. Why did that happen for a valid time answer: question-like hour phrasing (`в 5 часов`) produced a grounded time candidate, but generic `info_query` blocking still won before slot progress could be recorded.
  4. Why is that a contract bug: the runtime already had a grounded `time` candidate under active `expected_reply_type=time`, so blocking it discarded real slot progress.
  5. Why is this not the same as prior `P1.6h/P1.6m`: earlier blocks covered partial-datetime parity and alternate-slot capture, but not question-like hour-of-day phrasing colliding with info-interrupt arbitration.

- Root cause statement:
  - expected-reply info-interrupt arbitration is too aggressive for active booking `time` follow-ups: it blocks grounded hour-of-day answers before partial datetime progress can be recorded.

- Fix mechanism:
  - narrow the `expected_reply_blocked_by_info` rule for `EXPECTED_REPLY_TIME` so grounded hour-of-day answers remain in the booking slot path when there is no real info/price/style/reschedule intent
  - lock the behavior with deterministic message-endpoint tests and return `P1.6o6` to one fresh guarded `dev L2`

## Invariant

1. Real info interrupts (`price`, `duration`, `hours`, `location`, `style_reference`, `reschedule`, `verification`) must still block expected-reply capture when the user is actually switching topics.
2. No new phrase/regex hardcode may be added as the semantic owner for booking time answers.
3. Partial datetime progress must stay consistent with `P1.6h`: capturing time-only is allowed, but it must remain explicit that full datetime is still incomplete.
