## Root cause (mandatory)

- Symptom:
  - guarded `dev L2` rerun `p1.6o6-l2-dev-20260308-a1-r9` stopped with `semantic_valid=false`, `stop_reason=max_failures_reached:1`
  - failing turn: `dialog_id=1`, `turn_index=6`, message `В какое время можно записаться?`
  - family: `booking_slot_stall`

- Minimal reproduction:
  1. inspect `/tmp/booking_quality/p1.6o6-l2-dev-20260308-a1-r9/summary.json`
  2. inspect `/tmp/booking_quality/p1.6o6-l2-dev-20260308-a1-r9/responses.jsonl` for `message_id=LLM-QUAL-p1.6o6-l2-dev-20260308-a1-r9-001-06-a7035a`
  3. inspect `_send_policy_validation_collect_prompt()` in `truffles-api/app/routers/webhook/decision.py`
  4. inspect `_llm_quality_should_expect_booking_progress()` in `ops/diagnose.py`

- Evidence:
  - policy-core raw payload requests `action=collect`, `tool_action=calendar.list_slots`, `capability=bookability`, `resolution_mode=clarify_missing_time`, but carries `temporal_scope=none`
  - runtime correctly blocks the tool call with `validation_error=semantic_temporal_scope_missing`
  - fallback reply is valid missing-slot collect: `На какую дату и время вам удобно?`
  - however runtime meta/context records `expected_reply_reason=booking_prompt`, so guarded quality treats the turn as ordinary booking-progress opportunity instead of degraded collect

- Five Whys:
  1. Why did guarded quality fail: the turn was classified as `booking_slot_stall`.
  2. Why was it classified as stall: progress gate expected slot progress on a `time` turn inside active booking.
  3. Why didn’t the progress gate suppress it: suppression already exists for `expected_reply_reason=policy_core_degraded_collect`, but the turn emitted `booking_prompt`.
  4. Why did runtime emit `booking_prompt`: `_send_policy_validation_collect_prompt()` writes the expected-reply reason as ordinary booking prompt even though the path is a policy-validation degraded collect.
  5. Why is that wrong: the fallback is semantically a degraded slot-filling reprompt for a missing required field, not normal booking advancement, so the runtime contract drifts from the acceptance contract.

- Root cause statement:
  - policy-validation collect fallback reuses booking prompt text but advertises it under the wrong runtime reason (`booking_prompt` instead of `policy_core_degraded_collect`), causing guarded quality to misclassify valid degraded missing-slot repair as booking-progress stall.

- Fix mechanism:
  - make `_send_policy_validation_collect_prompt()` stamp expected-reply context with `policy_core_degraded_collect`;
  - add exact runtime regression for `semantic_temporal_scope_missing`;
  - rerun the guarded `dev L2` contour and verify that the blocker family disappears without weakening the oracle.
