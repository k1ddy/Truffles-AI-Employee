- Symptom:
  - the first valid `P1.6` dev realism run stayed `semantic_valid=false` with four critical semantic misses

- Minimal reproduction:

  2. `python3 - <<'PY'\nfrom app.services.pack_runtime_service import resolve_master_intent, get_pack_decision\nmsg='Когда у вас работают мастера?'\nprint(resolve_master_intent(message_text=msg, client_slug='demo_salon'))\nprint(get_pack_decision(msg, client_slug='demo_salon', intent_decomp={'intents':['other']}))\nPY`
  3. inspect failing turns in `/tmp/booking_quality/p1.6-l2-dev-seed42-r6/responses.jsonl` and `/tmp/booking_quality/p1.6-l2-dev-seed42-r6/trace_bundle.jsonl`

- Evidence:
  - `/tmp/booking_quality/p1.6-l2-dev-seed42-r6/summary.json`
    - `infra_valid=true`
    - `semantic_valid=false`
    - blocking reasons include `expected_action_mismatch`, `expected_reply_type_mismatch`, `wrong_action`, `handoff_miss`
  - failing turn `dialog_index=7 turn_index=2`
    - booking-start turn degraded to `policy_core_guard` clarify on timeout instead of contract-safe booking collect
  - failing turn `dialog_index=9 turn_index=1`
    - phrase `Когда у вас работают мастера?` degraded to `info_sections=["master"]` because timeout fallback let `master` resolver win on lexical overlap
  - direct resolver probe:
    - `resolve_master_intent("Когда у вас работают мастера?")` currently returns `explicit=True`, `reason=person_action_signal`

- Five Whys:
  1. Why did the run stay semantically invalid: timeout/error fallback still changes user meaning in degraded mode.
  2. Why does degraded mode change meaning: fallback path chooses semantic recoveries (`clarify`, `master`) that are not limited to protocol-safe defaults.
  3. Why is that a contract violation: `timeout_degrade` is allowed only as observable graceful degradation, not as a second semantic owner.
  4. Why did hours become master: `master` resolver treats `person + action` lexical overlap as explicit master intent even when the same phrase also carries hours anchors.
  5. Why did booking-start clarify instead of collect time: timeout-safe booking collect only activates for existing booking slot contexts, not for fresh booking starts where service is already known.

- Root cause statement:
  - `timeout_degrade` fallback is still allowed to perform semantic arbitration beyond boundary-safe rules: it misses a safe booking-start collect path and lets the master resolver overtake ambiguous hours phrases through lexical `person_action_signal`.

- Fix mechanism:
  - harden timeout fallback so fresh booking-start turns with resolved service degrade to slot-safe `datetime` collect instead of generic clarify
  - harden master resolver so `person_action_signal` does not become explicit master intent when hours anchors are present and no direct master/service signal exists
  - prove both behaviors with deterministic tests before rerunning `dev L2`
