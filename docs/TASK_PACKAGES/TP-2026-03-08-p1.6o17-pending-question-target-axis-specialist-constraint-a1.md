- Evidence:
  - `r12` no longer surfaced the `На какое время лучше записаться?` family; the bounded `P1.6o16` time-guidance owner is no longer the first blocker.
  - The generated scenario tagged `Могу ли я записаться к Айгерим?` as `ask_about_requested_slot`, and the default oracle expected `pending_question_act=ask_about_requested_slot` with `question_contract.expected_reply_type=time`.
  - Runtime instead returned `action=booking_prompt`, `intent=booking`, `pending_question_act=fill_requested_slot`, preserved `expected_reply_type=time`, and ignored the named specialist as a semantic owner signal.
  - `scripts/booking_dialog_scenarios.py` currently hard-binds `ask_about_requested_slot`, `slot_constraint`, `slot_compare`, and `mixed_fill_plus_question` to target `time`, so taxonomy has no explicit target-axis for `specialist`.
  - Existing master interrupt resolution still depends on direct/person/action signals or person-service relation; a bare named-specialist question like `Могу ли я записаться к Айгерим?` falls outside that contract.

- Five Whys:
  1. Why did the runtime repeat the generic time prompt: the turn was interpreted as ordinary booking collect, not as a specialist constraint/question under active collect.
  2. Why was it interpreted that way: the current contract models `pending_question_act`, but not the target dimension of that act (`time` vs `specialist` vs other slot axis).
  3. Why did the scenario/oracle expect the wrong family: taxonomy defaults currently map all new pending-question acts to `time`, so a specialist question can be mislabeled as `ask_about_requested_slot(time)`.
  4. Why didn't `P1.6o15` catch this: `P1.6o15` closed named-master questions with explicit master/person cues, but not bare named-specialist questions under active booking collect.
  5. Why did this only surface post-factum in `r12`: docs/TPs closed the operation axis for pending questions, but not the target-axis over which the operation is performed.

- Root cause statement:
  - after `P1.6o16`, the system still lacks an explicit target-axis for active pending-question interactions, so taxonomy/oracle over-compress specialist questions into time-slot tags, while runtime compresses bare named-specialist booking questions into ordinary `fill_requested_slot` collect.

- Fix mechanism:
  - extend the pending-question contract with explicit target semantics before adding more owners;
  - split specialist-constraint / specialist-compare expectations away from the closed `ask_about_requested_slot(time)` family;
  - then add only the bounded runtime owner for bare named-specialist booking questions under active collect.
