- Evidence:
  - Scenario tags the turn as `check_booking`.
  - Runtime kept `expected_reply_type=service_choice` and recorded `question_contract -> matched`.
  - `decision_meta` ended as `action=reply`, `intent=consult_reply`, `source=pack`, with `consult_question="Дизайн ногтей"`.
  - `check_booking` owner-path never ran, so the run failed on `expected_meta_mismatch`, `expected_trace_miss`, and `judge_fail`.

- Five Whys:
  1. Why did `r19` fail: the runtime replied from consult flow instead of entering booking-verification handling.
  2. Why did consult flow win: stale `service_choice` expected reply short-circuited before the operational booking turn could be arbitrated.
  3. Why was that short-circuit allowed: the expected-reply contract does not explicitly yield to booking-verification / booking-management turns.
  4. Why is that wrong: `check_booking` is not an answer to `service_choice`; it is a different operation over the dialog state and must take ownership.
  5. Why did this surface only now: `P1.6o21` removed the previous mixed-turn taxonomy false positive, so the next runtime family became visible.

- Root cause statement:
  - the expected-reply contract can consume stale `service_choice` context even when the incoming turn is an operational booking-verification request, so runtime ownership never reaches the existing `check_booking` path.

- Fix mechanism:
  - add a bounded expected-reply bypass / fail-closed guard for booking-verification and adjacent booking-management turns before slot-answer short-circuit;
  - keep the fix at the owner boundary, not as a phrase-specific response override;
  - add targeted message-endpoint regressions that prove `check_booking` wins over stale `consult_booking_cta` expected reply.
